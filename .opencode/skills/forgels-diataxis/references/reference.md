# Reference

Source: https://diataxis.fr/reference/ (fetched 2026-10-18)

Reference guides are technical descriptions of the machinery and how to operate it. They are information-oriented and serve WORK with propositional knowledge. Their only purpose is to describe, as succinctly as possible, in an orderly way. Content is led by the product, not by user needs.

Users need reference for truth and certainty: firm platforms to stand on while they work. One hardly reads reference; one consults it. It must be wholly authoritative, with no doubt or ambiguity. Like a map of the territory.

Auto-generated API docs alone are not all the documentation required, but generation from code is a powerful way to keep reference faithful.

## Key principles

- Describe and only describe. Neutral description is the imperative: austere, objective, factual. Explaining, instructing, discussing, and opining all run counter to reference. Link to how-to, explanation, and tutorials instead.
- Adopt standard patterns. Reference is useful when consistent: same place, same format, every time. No showing off vocabulary or style.
- Respect the structure of the machinery. Documentation structure mirrors product structure so gaps become visible and users can navigate both together.
- Provide examples. A usage example illustrates without drifting into instruction or explanation.

## Language

- State facts: "Django's default logging configuration inherits Python's defaults. It's available as ... and defined in ...".
- List exhaustively: sub-commands, options, operations, features, flags, limitations, error messages.
- Warn where appropriate: "You must use a. You must not apply b unless c. Never d."
